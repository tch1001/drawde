drawde · phase 1 — PDF reader tech

Candidate viewer technologies for the paper-reading pane. Sample document: Maldacena, The Large N Limit of Superconformal Field Theories and Supergravity (hep-th/9711200, 22 pages, equation-dense — a realistic stress test).
What drawde ultimately needs from a viewer: ① text-selection layer (select a derivation span), ② programmatic access to text/region coordinates (send the right crop + context to the AI), ③ custom overlays/annotations (anchor AI output to a spot in the paper), ④ smooth long-document scrolling. Judge the demos with those in mind.

PDFSlick live

MIT · pdf.js internals + state store

Middle ground: pdf.js's real viewer machinery (virtualized scrolling, zoom, find) minus Mozilla's UI chrome, exposed as a store you build UI around. Vanilla/React/Solid/Svelte.

EmbedPDF live

MIT · PDFium (WASM) engine · plugin system

Newer (2024+) open-source viewer on a PDFium WASM core — Chrome-grade rendering fidelity, plugin architecture with annotations, search, redaction. Framework-agnostic.

mupdf.js live

AGPL-3.0 (or commercial) · MuPDF → WASM

Not a viewer — an engine: very fast raster + structured text with per-block coordinates (great for the AI pipeline). Demo renders pages to PNG client-side and dumps text bboxes. AGPL is the catch.

Key takeaways

  • Everything free with a UI is pdf.js underneath — except EmbedPDF, which is PDFium (Chrome's engine) compiled to WASM. Choosing pdf.js-family vs EmbedPDF is the real fork in the road.
  • Best geometry APIs (for feeding equation regions to the AI): mupdf.js structured text > PDFium per-char rects > pdf.js getTextContent. mupdf's AGPL is a problem for a closed SaaS; note we could still use it server-side if drawde's backend is open-sourced, or pay Artifex.
  • @react-pdf-viewer is dead (archived 2026-03, CVE-pinned) — despite still topping search results. Lector is the living successor for headless React primitives.
  • react-pdf-highlighter proves the interaction we want (text + area highlights with rect data) but is unmaintained — fork-fodder, not a dependency.
  • Commercial tier (Apryse/Nutrient) is polished but sales-quoted $$$$; Adobe Embed is free but a black-box iframe with no text-geometry access — bad fit for the AI pipeline.
  • pdf.js major-version churn (v4→v6 in ~2 years) regularly breaks wrappers — favor thin wrappers or direct use.
  • A viable hybrid: pdf.js (or EmbedPDF) for the viewing pane + an engine (mupdf/PDFium server-side) for extraction feeding the AI.
